🔴 Vulnérabilités CRITIQUES
CRITIQUE Fichiers de sauvegarde SQL accessibles publiquement
Fichier trouvé : s/backup_20260901_095659.bak et s/files.zip dans un dossier web accessible.
Un hacker peut télécharger directement la base de données complète via http://site/s/backup_20260901_095659.bak — sans aucune authentification. Cela expose TOUS les mots de passe, utilisateurs et données métier.
🔧 CORRECTION :
Déplacer les backups HORS du dossier web (ex: C:\Backups\) ou bloquer l'accès dans web.config avec <location path="s"><system.web><authorization><deny users="*"/>
CRITIQUE Clés SSH exposées à la racine du projet web
Fichiers trouvés : ssh et ssh.pub à la racine du projet.
Si ces fichiers sont accessibles via le serveur web, un attaquant peut récupérer la clé privée SSH et accéder au serveur sans mot de passe.
🔧 CORRECTION :
Supprimer ces fichiers du projet web immédiatement. Ne jamais stocker de clés SSH dans un dossier web. Révoquer et régénérer les clés compromises.
🟠 Vulnérabilités ÉLEVÉES
ÉLEVÉ Lockout côté Session uniquement — Contournable
Le blocage après 5 tentatives (MAX_ATTEMPTS=5, LOCKOUT_SECONDS=60) est stocké en Session ASP.NET, pas en base de données.
Un hacker peut contourner en ouvrant un nouvel onglet / navigateur / IP différente — la session repart à zéro. Brute-force illimité possible.
🔧 CORRECTION :
Stocker les tentatives en base (table USERS, colonne FAILED_ATTEMPTS + LOCKED_UNTIL) et bloquer par USERNAME, pas par session.
ÉLEVÉ ArticleHandler.ashx — Vérification de session incohérente
s/files/ArticleHandler.ashx.cs vérifie Session["IDUser"] (minuscule "d") alors que la session est initialisée avec Session["IDUSER"] (majuscule).
Cette incohérence peut rendre le handler accessible sans authentification valide selon la casse du serveur.
🔧 CORRECTION :
Remplacer Session["IDUser"] par AuthHelper.RequireApiAuth(context) pour une vérification centralisée et cohérente.
ÉLEVÉ Erreurs SQL exposées à l'utilisateur
Dans Login.aspx.cs, les erreurs SQL sont affichées directement : ShowError("❌ Erreur SQL: " + sqlEx.Message).
Un attaquant peut obtenir le nom du serveur SQL, la structure de la base, les noms de tables via des messages d'erreur.
🔧 CORRECTION :
Afficher un message générique ("Erreur de connexion") et logger l'erreur détaillée côté serveur uniquement.
🟡 Vulnérabilités MOYENNES
MOYEN Absence de protection CSRF sur les formulaires
Aucun token CSRF explicite n'est vérifié dans les handlers .ashx. Un attaquant peut forger des requêtes depuis un site tiers pour déclencher des actions (ajout/suppression d'articles) au nom d'un utilisateur connecté.
🔧 CORRECTION :
Ajouter un token CSRF dans chaque requête AJAX et le valider côté serveur dans les handlers.
MOYEN Fichier test.aspx à la racine
Le fichier test.aspx est présent à la racine. Les pages de test laissées en production exposent souvent des informations système, des diagnostics ou des fonctionnalités non sécurisées.
🔧 CORRECTION :
Supprimer test.aspx en production ou le protéger avec une restriction d'accès IP.
MOYEN Logs d'erreur accessibles dans App_Data
Les fichiers authmodule_error.log, authmodule_errors.log, security.log sont dans App_Data/. Si IIS est mal configuré, ces logs peuvent être téléchargés et révèlent des stack traces, IPs, usernames.
🔧 CORRECTION :
Vérifier que App_Data est bien protégé dans web.config. Idéalement, stocker les logs hors du dossier web.
MOYEN Redirection ouverte via Query String
Request.QueryString["msg"] est utilisé pour afficher des messages. Bien que non redirigé directement, ce pattern peut être exploité pour du phishing si une redirection est ajoutée plus tard.
🔧 CORRECTION :
Valider strictement les valeurs acceptées (whitelist) et ne jamais utiliser un paramètre URL comme URL de redirection.
🟢 Vulnérabilités FAIBLES
FAIBLE Mots de passe legacy en texte clair en base
PasswordHelper.cs accepte encore les mots de passe en texte clair (if (storedHash == password)) pour la compatibilité legacy. Si la base est compromise, ces comptes sont immédiatement exposés.
🔧 CORRECTION :
Forcer la migration de TOUS les mots de passe legacy vers PBKDF2 et supprimer la vérification en texte clair.
FAIBLE Absence d'en-têtes de sécurité HTTP
Aucun en-tête de sécurité visible : pas de X-Frame-Options, Content-Security-Policy, X-Content-Type-Options. Risque de clickjacking et XSS.
🔧 CORRECTION :
Ajouter dans web.config : X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Content-Security-Policy.
✅ Points positifs (bien sécurisés)
OKRequêtes SQL paramétrées — Protection contre l'injection SQL
Toutes les requêtes utilisent cmd.Parameters.AddWithValue(). Aucune concaténation de chaîne SQL détectée. ✅
OKHachage PBKDF2 avec sel aléatoire (100 000 itérations)
Les nouveaux mots de passe utilisent PBKDF2 avec sel cryptographique. Comparaison en temps constant (FixedTimeEquals). ✅
OKToken de session validé en base de données
Chaque requête vérifie le SESSION_TOKEN en base via ValidateSessionToken(). Empêche la réutilisation de sessions volées. ✅
OKModule d'authentification centralisé (AuthModule.cs)
Toutes les pages .aspx et handlers .ashx passent par AuthModule. Pas de page oubliée sans protection. ✅
OKVérification des permissions par rôle
Les handlers vérifient les permissions via RequirePermission() et RequireApiAuth(). ✅
